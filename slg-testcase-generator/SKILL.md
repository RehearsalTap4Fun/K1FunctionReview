# SLG 测试用例生成

---

## 模式选择：先确定交付方式

- 当请求来自 `review-k1-function` 的需求对齐后静态预审，读取 [K1 静态用例规则](references/static_acceptance.md)，按已确认且回读的开发文档校准已有用例、补齐缺口，交付本地 Markdown。保留稳定需求 ID、用例 ID、来源定位和文档版本。
- 此模式覆盖每项需求及文档支持的主流程、边界和异常，不设用例数量或累计时间上限。先完成 `review-k1-function` 的文档对齐；无法确认的需求如实记录，不能编造预期或以数量上限丢弃需求。
- K1 静态模式仅按本节与 `references/static_acceptance.md` 执行；不读取在线项目账号配置，不执行七步 Google Sheets 流程，也不创建或更新在线文档。下文从“项目配置”到文末的强制规则、预计数量和 Google 写表要求仅适用于独立的标准在线模式，不作为 K1 静态模式的前置或完成条件。
- 独立的标准在线用例任务使用下方既有七步 Google Sheets 流程；先读取项目配置，保留 QA 原有的用例编写与写表要求。

## 🔧 标准在线模式：项目配置（使用前必读）

> **K1 团队共享包**：接入方式见 [ONBOARDING.md](ONBOARDING.md)。包内 `K1-testcase-config/` 保留团队配置、知识库和需求/用例参考；标准流程仍读取项目工作区的 `testcase-config/`。登录凭证、个人配置和历史输出由协作者在本地准备。

> 本 Skill 为**通用基础层**，适用于所有 SLG 项目。项目特有的配置（路径、ID、特色玩法知识等）存放在各项目工作区的 `testcase-config/` 目录中。

**标准在线模式强制规则**：在执行该模式的用例生成流程之前，必须先完成以下步骤：

1. 读取当前项目工作区的 `testcase-config/project_config.md`，获取项目级配置（Drive 路径、配置表 ID 等）
2. 检查 `testcase-config/game_knowledge/` 目录，了解项目特色玩法知识库
3. 若 `testcase-config/project_config.md` 不存在，提示用户：「当前项目未配置 testcase-config/，请参考通用 Skill 中的 project_config.template.md 创建」

> 本文件中涉及路径/ID 的地方，标注了 `{项目配置.xxx}` 的，均需从项目配置文件中读取实际值。

## ⛔ 标准在线模式：五条铁律（违反=失败）

| # | 铁律 | 说明 |
|:-:|------|------|
| 1 | **7步流程不可跳过** | 阅读需求→判断复杂度→需求确认→知识库→编写规则→生成用例→写入Sheets，每一步都必须执行 |
| 2 | **生成前必须输出检查清单** | 先输出「关键词识别→模板触发→预计用例数」，再生成用例。没有输出分析就直接生成=流程违规 |
| 3 | **有据可查，图片优先** | 界面元素/交互形式必须来自 UX 图，不能凭空假设。**PRD 有配图时，以图片展示的实际形态为准**，禁止仅凭文字描述脑补交互方式。**但图片中的示例数据（如具体任务名称、数值）可能是假图占位**，不等于确定需求——检查项照写，预期结果用通用描述，备注标注待确认 |
| 4 | **检查点该合并须合并，密度不要过高** | 同一验证维度、仅前置条件不同的应合并为一个检查点，不要拆成多个「仅 1 条用例」的检查点。检查点名称必须比模块名更具体。详见 [core_writing_rules.md](references/core_writing_rules.md)「模块与检查点划分规则」+「检查点合并与命名规范」 |
| 5 | **🔴 执行成本最低** | 检查点必须按状态流推进，同一前置状态下能验的全部验完再进下一状态，**禁止按 UI 元素类型拆检查点导致测试人员反复准备前置数据**。详见 [core_writing_rules.md](references/core_writing_rules.md)「执行成本最低原则」 |

## 🔴 标准在线模式：核心规则（10条）

| # | 核心规则 | 说明 |
|:-:|----------|------|
| 1 | **元素全覆盖** | 界面看到什么验证什么（按钮/图标/文本/数值） |
| 2 | **状态全拆分** | 多状态每种单独验证（高亮/置灰/A>B/A=B/A<B） |
| 3 | **操作链全跟踪** | 一个操作触发后完整跟踪所有响应 |
| 4 | **入口必须3条** | 图标 + 名称 + 点击响应 |
| 5 | **新功能验正反** | 开启时显示 + 不开启时不显示，都要验证 |
| 6 | **配置必标ID，数值用n** | 格式：`配置表XXXX-字段名`，不能只写"符合配置"。**配置表数值禁止写具体值，用 `n` 代替，边界用 `n-1`/`n+1`** |
| 7 | **不确定就标注** | 用 ⚠️待确认 / ⚠️推测 标记 |
| 8 | **置灰必验点击** | 显示置灰 + 点击无响应，两条用例 |
| 9 | **开启前后对比** | 新功能必须验证开启前后行为差异 |
| 10 | **检查点该合并须合并** | 每个检查点通常 2~10 条用例；同一验证维度、仅前置条件不同的须合并，**避免拆成多个仅 1 条的检查点**；检查点名称要比模块名更具体，不得与模块名完全相同 |

> 详细写法规则见 [core_writing_rules.md](references/core_writing_rules.md)

## ⚠️ 标准在线模式：用例生成强制流程（必须遵循）

> **在标准在线模式生成用例之前，必须完成以下检查流程，不可跳过！**

| 步骤 | 内容 | 说明 |
|:----:|------|------|
| **1** | **阅读需求** ⭐ | PRD + UX 图必须完整查看，详见 [1_analysis.md](references/1_analysis.md)。**Google Sheet 读取：必须使用 `scripts/excel_tool.py`**（禁止使用 WebFetch/curl） |
| **2** | **判断功能类型与复杂度** | ①判定功能类型（A新系统/B优化/C礼包/D活动）→ **必须读取**对应策略文件（见下方「功能类型策略」表）。②判断复杂度：小型100-200条 / 中型300-600条 / 大型1000-1500条。**⚠️ 若判定为大型/复杂（>400条或多系统联动），必须走步骤2a** |
| **2a** | **🔴 输出模块图（大型/复杂必做）** | 详见下方「复杂系统专用流程」。**禁止跳过此步直接生成用例！** |
| **2b** | **🔴 参考材料确认（Type B 必做）** | 判定为 Type B（功能优化）时，检查用户是否已提供原版PRD/原版用例。**若未提供，主动向用户确认**。如用户表示"之前生成过"但无链接，使用 Drive 全局搜索历史用例，**搜索结果必须先展示给用户确认后再读取**。详见 [type_b_update.md](references/type_b_update.md)「参考材料获取」+「历史用例自动检索」章节 |
| **3** | **需求确认** ⭐ | 识别待确认内容，详见 [0_requirement_confirm.md](references/0_requirement_confirm.md) |
| **4** | **阅读游戏知识库** | 自动检测关键词触发，详见下方「知识库触发规则」。**涉及战斗/派兵时，必须输出「场景清单」** |
| **5** | **阅读编写规则** ⭐ | **必须**读取 [core_writing_rules.md](references/core_writing_rules.md)，执行关键词识别→触发阅读 [scenario_patterns.md](references/scenario_patterns.md) 中**索引表 + 匹配章节**（⚠️ 不要全文读取，只读索引→跳转触发的章节） |
| **5b** | **生成前检查** ⭐ | **必须**读取 [execution_checklist.md](references/execution_checklist.md)「生成前必做」章节逐条确认。大型系统还需确认「大型复杂系统生成前专项检查」 |
| **6** | **生成用例** | **必须由主 agent 分批生成（禁止子任务生成用例内容）**。小型/中型：一次生成。大型/复杂：按模块图逐模块生成。生成时按步骤2策略文件中的「必选模块清单」逐一覆盖，按需跳转读取 [common_scenarios.md](references/common_scenarios.md) 中对应模板编号。详见下方「用例生成方式选择」 |
| **6b** | **生成后自检** | 按 [execution_checklist.md](references/execution_checklist.md)「生成后自检」+「执行检查清单」逐项检查；**重点自检：是否把本该合并的检查点拆得过密（多个仅 1 条）？** 该合并的须合并后再写入 |
| **7** | **写入 Google Sheets（仅标准模式）** ⭐ | **必须**按 [file-operations-compact.md](references/file-operations-compact.md) 流程写入。**写入前建议**对导出的用例 JSON 运行 `python scripts/validate_cases.py 文件.json`，若有检查点过密等提示可先合并再写入 |

### 🔴 复杂系统专用流程（步骤2a，大型/复杂必做）

> **判定标准**：预计用例 >400 条，或 PRD 明确涉及多系统联动（如：英雄+战斗+派兵+战报+副本）

**⚠️ 复杂系统禁止直接生成用例！必须先完成以下步骤：**

#### 第一步：输出《模块图》

必须输出以下格式的模块图，**先锁定覆盖范围**：

```markdown
## 《功能名称》模块图

| # | 模块名称 | 子检查点 | 预计用例数 | 备注 |
|:-:|----------|----------|:----------:|------|
| 1 | 未获得-界面显示 | 入口、主界面元素、详情弹窗 | 25 | |
| 2 | 获得-召唤/解锁 | 召唤流程、首次获得、重复获得 | 15 | |
| 3 | 核心玩法-xxx | xxx | 60 | 含状态矩阵 |
| 4 | 养成-等级/星级 | 升级、满级、配置验证 | 30 | |
| 5 | 派兵界面 | 详情模式、编队、选择限制 | 40 | ⭐必选 |
| 6 | 战斗场景 | 野外pvp/pve、驻防、集结、副本… | 50 | ⭐必选 |
| 7 | 战报显示 | 日志页、详情页、技能显示 | 20 | ⭐必选 |
| 8 | 红点 | 触发、消失、层级联动 | 15 | ⭐必选 |
| 9 | 多入口一致性 | 各界面数据同步 | 10 | ⭐必选 |
| 10 | 数据兼容 | 跨服、老版本、重启 | 20 | |
| 11 | 通用检查 | 异常、兼容、本地化… | 50 | 固定模板 |
| | **合计** | | **335** | |
```

#### 第二步：检查必选模块

模块图输出后，**必须自检以下必选模块是否存在**：

| 必选模块 | 触发条件 | 最少用例数 |
|----------|----------|:----------:|
| **派兵界面** | PRD 涉及英雄/部队/战斗 | 20条 |
| **战斗场景覆盖** | PRD 涉及战斗/技能/buff | 30条 |
| **战报显示** | PRD 涉及战斗 | 10条 |
| **红点** | 有新功能入口 | 10条 |
| **多入口一致性** | 功能在多个界面有入口/展示 | 8条 |
| **配置表验证** | PRD 提及配置表 | 按表覆盖 |
| **数据兼容** | Type A 系统功能 | 15条 |

**若必选模块在模块图中缺失，必须补充后再进入生成阶段！**

#### 第三步：分模块两阶段生成

> **每个模块都走「阶段一：骨架 → 阶段二：填充」，先锁覆盖范围再填细节**

**阶段一：输出用例骨架（仅结构，不写详细步骤和预期）**

按模块图顺序，对当前模块输出骨架：

```markdown
## 模块X：xxx（骨架）

| 编号 | 检查点 | 简要预期 |
|------|--------|----------|
| XX_001 | 入口显示 | 入口图标/名称/点击 |
| XX_002 | 主界面-元素总览 | 包含A、B、C、D元素 |
| XX_003 | 主界面-按钮A | 样式、状态、点击响应 |
| ... | ... | ... |
| 本模块骨架共 X 条 | | |
```

**骨架输出后自检**：
- [ ] 检查点是否与模块图一致
- [ ] 每个界面是否有「元素总览」
- [ ] 必选验证维度是否缺失（红点/配置表/状态切换等）
- [ ] 条数是否与模块图预估接近

**阶段二：按骨架填充完整用例**

将骨架中每条展开为完整的 JSON 格式用例（编号+功能模块+检查点+操作步骤+预期结果+备注）。

**逐模块循环**：模块1（阶段一→阶段二）→ 模块2（阶段一→阶段二）→ … → 所有模块完成 → 汇总合并 → 检查总数

### 🔴 配置数值写法检查（步骤6生成前必做）

> **在填充用例的预期结果和备注之前，必须重新读取 [core_writing_rules.md](references/core_writing_rules.md) 中「配置数值写法规范」章节（搜索关键词 `配置数值写法规范`），并执行以下检查：**

**第一步：整理配置表对照表**

从 PRD 中提取所有涉及配置的数值，整理为对照表：

```markdown
## 配置表对照表

| 数值项 | PRD原文 | 分类 | 写法 |
|--------|---------|------|------|
| 转盘格子数 | 12个格子 | 需求固定（结构） | 直接写"12个格子" |
| 各格子奖励内容 | 紫色宝石×2... | 配置可调（奖励类） | "奖励内容与配置一致" + 备注配置表ID |
| 各次抽取价格 | $0→$1.99→... | 配置可调（价格类） | "价格与配置一致" + 备注配置表ID |
| 概率权重 | 98.08%... | 配置可调（数值类） | "概率与配置一致" + 备注配置表ID |
```

**第二步：按分类决定写法**

| 分类 | 判断标准 | 预期结果写法 | 备注写法 |
|------|----------|-------------|----------|
| **需求固定** | PRD写死且极少变动的结构/逻辑 | 直接写具体值 | 无需标注 |
| **配置可调** | 数值/奖励/价格/概率/时间等 | "与配置一致"，禁止写死具体数值 | `配置表XXXX-字段名` |

**配置可调的常见场景**（必须用"与配置一致"）：
- 数值类：开启天数、触发次数、持续时间、限购次数、CD时间
- 奖励类：奖励道具种类、道具数量、道具品质
- 价格类：礼包价格、商品价格、折扣比例
- 内容类：礼包内容物、活动奖池、掉落物品
- 概率类：掉落率、触发概率、权重

**第三步：检查是否将配置数值误解读为功能特性**

> **🔴 禁止将配置数值解读为功能特性**：当PRD中某个配置数值恰好为特殊值（如$0、100%、1次等）时，**不应将其拆为独立功能模块**，而应统一归入对应流程按配置可调处理。

| 配置数值 | ❌ 错误：拆为独立模块 | ✅ 正确：归入对应流程 |
|----------|----------------------|----------------------|
| 第1次价格=$0 | "首次免费抽取"模块 | 归入"抽取流程"，价格与配置一致 |
| 某道具概率=100% | "必得道具"模块 | 归入"概率验证"，概率与配置一致 |
| 限购次数=1 | "唯一购买"模块 | 归入"限购验证"，次数与配置一致 |

**判断标准**：PRD是否用**文字明确描述**了该机制（如写了"首次免费"）？如果只是数值表中的值，按配置可调处理。

**⚠️ 如果未输出配置表对照表就直接生成用例，视为流程违规！**

**如果未输出以上分析就直接生成用例，视为流程违规！**

### 🔴 用例生成方式选择（步骤6必读）

> **质量优先，禁止为了速度牺牲质量。**

#### 强制规则：主 agent 分批生成

**用例生成必须由主 agent 直接完成**，按模块分批生成，每批一个模块。禁止使用子任务（subagent/Task工具）生成用例内容。

**原因**：子任务（尤其是 fast 模型）无法正确理解和执行检查点归并规则、模块划分逻辑等需要判断力的工作，会导致：
- 每条用例检查点名称都不同（检查点粒度失控）
- 输出格式不符合合并要求
- 各子任务之间风格不一致

#### 正确的分批生成流程

1. 按模块图顺序，**逐模块生成**（每次生成一个模块的完整用例）
2. 每个模块生成前，回顾 [core_writing_rules.md](references/core_writing_rules.md) 中的检查点归并规则
3. 每个模块生成后，立即检查检查点粒度（2-10条/检查点）
4. 所有模块完成后，合并、重编号、写入

#### 子任务的允许用途

子任务**仅允许**用于以下机械性工作，**禁止**用于用例内容生成：
- 格式转换（JSON对象 → 二维数组）
- 数据合并与重编号
- 文件读写操作
- Google Sheets API 调用

#### 备选方案：子任务生成（仅当主 agent 明确无法完成时）

如果因上下文长度等客观限制，主 agent 确实无法一次完成某个模块的生成，可使用子任务作为**备选方案**，但必须：

1. 子任务 prompt 开头必须写：`请先读取 references/subagent_rules_compact.md 获取完整编写规则，严格遵循其中的检查点归并规则和输出格式。`
2. 输出格式必须为带合并的二维数组：`[["编号","模块","检查点","操作步骤","预期结果","备注"], ...]`
3. 禁止在 prompt 中写"一条用例只验证一个检查点"
4. 主 agent 收到结果后必须逐条检查检查点粒度，不合格的必须重新归并

### 完成后自检

用例写入完成后，自动检查以下情况：

| 检查项 | 触发条件 |
|--------|----------|
| **涉及原有功能** | PRD 关联已有系统（如英雄、战斗、商城等）但用例未覆盖相关配置 |
| **PRD 提及配置表** | PRD 中提到了配置表 ID 但用例未验证对应配置项 |
| **🔴 必选模块缺失** | 复杂系统的必选模块（派兵/战斗/战报/红点/多入口）中有模块为 0 条 |
| **🔴 场景清单未覆盖** | 战斗/派兵场景清单中「✅」的场景在用例中无对应 |
| **🔴 矩阵未覆盖** | 状态/条件矩阵中有行在用例中无对应 |
| **🔴 配置数值写死** | 预期结果中存在配置可调的具体数值（价格/奖励内容/数量/概率等），应改为"与配置一致" |
| **🔴 配置表标注缺失** | 涉及数值/概率/时间/奖励的用例备注中缺少配置表ID+字段名 |
| **🔴 配置值误拆模块** | 将配置数值的特殊值（如$0、100%、1次）解读为独立功能模块（如"首次免费"、"必得"），PRD未明确描述该机制时应归入对应流程 |

**如果检测到以上情况**，提醒用户：

```
✅ 用例已写入 Google Sheets

⚠️ 检测到以下问题：
- 🔴 必选模块「xxx」为 0 条，建议补充
- 🔴 战斗场景「xxx」已标记涉及但无对应用例
- ⚠️ 配置表 xxxx 未验证
- 是否需要补充？请说"补充"
```

**如果未检测到问题**，只提示完成：

```
✅ 用例已写入 Google Sheets（共 xxx 条）
```

## 输出格式

### JSON 格式

```json
[
  ["DK2_001", "排行榜", "入口", "检查活动主界面", "显示排行榜入口", ""],
  ["DK2_002", "", "", "", "入口图标符合需求", ""],
  ["DK2_003", "", "", "点击排行榜入口", "正确进入排行榜界面", ""]
]
```

### 字段说明

| 列 | 字段 | 规则 |
|----|------|------|
| A | 编号 | 必填，格式：`前缀_三位数字` |
| B | 功能模块 | 同模块第一条填写，后续写 `""` → 自动合并 |
| C | 检查点 | 同检查点第一条填写，后续写 `""` → 自动合并 |
| D | 操作步骤 | 同操作第一条填写，后续写 `""` → 自动合并 |
| E | 预期结果 | **必填**，每条用例必须有预期结果 |
| F | 备注 | 可选：配置表ID、本地化、⚠️待确认 |
