# 人工用例编写风格分析

> 基于「沙滩寻宝」用例（290条）的深度分析

---

## 一、整体结构特点

### 1. 模块划分策略

人工用例采用**功能驱动**的模块划分，而非流程驱动：

| 模块类型 | 示例 | 用例数量 |
|----------|------|:--------:|
| **核心玩法** | 普通关卡、保底关卡、特殊关卡 | 82 |
| **商业化** | 成就礼包、兑换商店、常驻礼包 | 63 |
| **辅助系统** | 排行榜、红点、累计活动 | 49 |
| **通用检查** | 异常、本地化、兼容性、合规性 | 96 |

### 2. 用例编号规则

```
GACHA_001 ~ GACHA_290
前缀_三位数字序号
```

- 使用活动类型缩写作为前缀（GACHA）
- 连续编号，不跳号
- 不按模块分段编号

## 二、检查点细化模式

### 1. 操作与预期结果的1:N关系

人工用例中，**同一操作步骤可对应多条预期结果**，每个预期结果独立一条用例：

```
| GACHA_023 | | | 1.抽奖道具足够\n2.点击消耗1个抽奖道具按钮 | 立即播放选方向动画，符合需求 |
| GACHA_024 | | | | 动画播放完毕后立即朝该方向移动一格 |
| GACHA_025 | | | | 实际消耗1个抽奖道具 |
| GACHA_026 | | | | 累计消耗+1 |
| GACHA_027 | | | | 弹出积分增加跑马灯，图标、文本、实际增加积分符合本次活动 |
```

**关键发现**：
- 操作步骤列为空时，表示继续上一条的操作步骤
- 功能模块列为空时，表示继续上一条的功能模块
- 检查点列为空时，表示继续上一条的检查点
- 这种写法需要脚本自动合并单元格

### 2. 检查点命名规范

| 类型 | 命名示例 | 说明 |
|------|----------|------|
| 界面类 | 棋盘、弹窗、界面 | 整体UI检查 |
| 功能类 | 单抽、10抽、兑换 | 核心操作 |
| 状态类 | 触发条件、解锁、显示 | 状态变化 |
| 流程类 | 过关、循环、跨天 | 流程节点 |
| 边界类 | 特殊情况、中途打断 | 异常处理 |

## 三、预期结果编写规范

### 1. 具体化描述

人工用例的预期结果非常**具体**：

```
❌ AI常见写法：界面显示正常
✅ 人工写法：8列*8行个云雾格子

❌ AI常见写法：符合配置
✅ 人工写法：x符合配置的数量（并在备注标注配置表2121）

❌ AI常见写法：显示倒计时
✅ 人工写法：为当前时间到当日utc零点，实时刷新
```

### 2. 隐式前置条件

预期结果中常包含隐式前置条件：

```
"弹窗内展示的是第8列第m行的奖励、普通格子奖励总和、匹配奖励总和"
└── 隐式条件：玩家中途解锁了部分匹配奖励
```

### 3. 状态变化描述

强调状态的**前后对比**：

```
"限购次数-1"
"道具实际减少x"
"红点消失"
"按钮变为"已购买""
```

## 四、备注使用规范

### 1. 配置表引用格式

```
2121              - 只有表ID
2121\nA_ARR_array - 表ID + 字段名（换行分隔）
2124\n1是右\n2是上\n3是下 - 表ID + 枚举值说明
```

### 2. 本地化标记

```
本地化  - 涉及UI文本时标记
```

### 3. 补充说明

```
"随机逻辑服务器写的，不走配置"  - 技术实现说明
"多试几关保底关卡"  - 测试建议
"回原服才收到"  - 特殊行为说明
"此模块要拓展要检查的前提场景，具体功能具体分析"  - 灵活处理提示
```

## 五、模块内用例组织模式

### 1. 从正向到边界的递进

以「普通关卡」为例：

1. **初始状态**：棋盘显示（8条）
2. **正向流程**：单抽（9条）→ 10抽（4条）→ 过关（6条）→ 循环（1条）
3. **附属功能**：阶段奖励（3条）
4. **边界场景**：中途打断（3条）→ 特殊情况（2条）

### 2. 遍历拆分策略

人工用例中，**遍历并非每项都拆分**：

```
✅ 独立拆分：
| GACHA_076 | | 匹配奖励 | 踩中了1个类型1特殊道具 | 类型1奖励道具的第一个特殊道具点亮 |
| GACHA_078 | | | 踩中了2个类型1特殊道具 | 类型1奖励道具的第一、二个特殊道具点亮 |
| GACHA_079 | | | 踩中了3个类型1特殊道具 | 类型1奖励道具的第一、二、三个特殊道具点亮 |

✅ 合并处理：
| GACHA_088 | | 遍历 | 遍历其他三个类型的匹配奖励 | 与上方类型1表现一致 |
```

**规律**：
- 状态变化关键点（1→2→3）需要拆分
- 同质化验证（类型2/3/4与类型1相同）可以合并
- 配置档位验证可以用"遍历所有档位"

## 七、对AI生成用例的优化建议

### 1. 减少冗余，增加关键点

- **当前AI问题**：每个UI元素都独立一条，导致用例过多但深度不足
- **人工策略**：UI元素适度合并，核心流程深度拆分

### 2. 预期结果要具体

- **当前AI问题**：大量"符合配置"、"符合需求"
- **人工策略**：写具体数值、具体文案、具体表现

### 3. 操作步骤要完整

- **当前AI问题**：操作步骤过于简单
- **人工策略**：包含前置条件，如"1.抽奖道具不足\n2.点击消耗1个抽奖道具按钮"

### 4. 合理使用合并

- **当前AI问题**：要么全拆分，要么全合并
- **人工策略**：关键变化点拆分，同质验证合并

### 5. 备注更精准

- **当前AI问题**：只标配置表ID
- **人工策略**：表ID + 字段名 + 必要说明

## 十、Type A vs Type C vs Type D 用例差异

### 1. Type D（运营活动）特征

- **操作流程为主**：单抽、10抽、过关、循环
- **商业化必选**：礼包、兑换、排行榜
- **数据周期**：活动期内有效
- **遍历策略**：同质合并（类型2/3/4与类型1一致）

### 2. Type A（系统功能）特征

- **状态管理为主**：未获得 → 已获得 → 升级
- **临界值验证**：N-1 → N 的状态变化
- **反向验证**："进度不增加"场景
- **增益多层验证**：弹窗 → 详情界面 → 城市增益 → 实际效果
- **数据永久**：跨服、老版本兼容更重要

### 3. Type C（触发礼包）特征

- **触发条件验证**：界面打开触发、操作次数触发
- **多期礼包逻辑**：第一期/第二期切换、共存、优先级
- **礼包生命周期**：触发→显示→购买→CD→再次触发
- **多礼包共存**：共用入口、独立倒计时、页签切换
- **特殊情况处理**：触发状态保持、跨天保持、倒计时边界
- **遍历策略**：各档位遍历、各期遍历
- **关键边界**：
  - 未达到触发条件（x-1次）vs 达到触发条件（x次）
  - 正确界面 vs 非触发界面
  - 礼包已触发未购完 vs 购买完后再触发
  - 第一期结束时刻 vs 第二期开启时刻

### 4. 通用检查点

三种类型共享的固定模板：
- 异常场景（快速点击、home键、重启）
- 用户体验（数值合理性、操作合理性）
- 本地化（国际服、国服）
- 兼容性（分辨率、系统、屏幕）
- 合规性（文化局、gacha行为）

## 十一、通用用例设计模式（V7.3新增）

> 基于「集卡图鉴-回收模块」用例思路分析提炼

### 模式A：流程覆盖策略

**核心思路**：先用简单情况过一遍主流程，再覆盖边界条件

```
1. 简单场景走通主流程
2. 边界条件逐一覆盖
3. 异常情况补充
```

### 模式B：临界值验证

适用于：数量限制、解锁条件、触发阈值

| 场景 | 验证点 | 示例 |
|------|--------|------|
| 条件 - 1 | 不满足，功能不可用 | 仅有1张卡（需保留），不可回收 |
| 条件 = 临界值 | 刚好满足，功能可用 | 有2张卡，可回收1张 |
| 条件 > 临界值 | 超过，功能正常 | 有n张卡，可回收n-1张 |
| 条件 >> 临界值 | 大数值边界 | n>100，显示正常 |

### 模式C：输入框边界验证

适用于：数量输入、金额输入、搜索输入

| 输入类型 | 预期 |
|----------|------|
| 有效范围内 | 正常输入保存 |
| 最小值边界（0） | 无法输入 |
| 最大值边界+1 | 无法输入或自动修正 |
| 负数 | 无法输入 |
| 小数 | 无法输入 |
| 空值/空格 | 无法输入 |
| 特殊字符/表情 | 无法输入 |

### 模式D：批量操作状态覆盖

适用于：一键全选、批量删除、批量操作

| 前置状态 | 操作 | 验证点 |
|----------|------|--------|
| 无选择 | 批量操作 | 全部生效 |
| 部分选择（未修改） | 批量操作 | 覆盖之前选择 |
| 部分选择（已修改数量） | 批量操作 | 恢复默认最大值 |
| 批量后 | 批量取消 | 全部恢复初始状态 |
| 批量后 | 手动调整 | 状态正确更新 |

### 模式E：位置遍历验证

适用于：列表操作、删除操作、移动操作

- 首位操作
- 中间位置操作
- 末位操作
- 翻页后操作（超出一页时）

### 模式F：结果池刷新验证

适用于：回收、删除、消耗后的列表更新

| 验证点 | 说明 |
|--------|------|
| 列表刷新 | 操作后列表正确刷新 |
| 剩余项排序 | 剩余物品排序正确 |
| 空状态 | 全部操作完显示空状态提示 |
| 实际到账 | 获得的货币/奖励正确到账 |

### 模式G：组合覆盖

适用于：多类型、多数量、跨容器场景

| 场景 | 覆盖点 |
|------|--------|
| 单类型单数量 | 基础验证 |
| 单类型多数量 | 数量计算 |
| 多类型多数量 | 组合选择 |
| 跨容器/跨类别 | 混合场景 |
| 超出显示限制 | 换行/滑动 |

## 十二、用例设计四原则（V7.4新增）

> 基于「英雄皮肤系统」用例优化分页提炼

### 原则1：规则定义后沿用

**做法**：给出明确的规则定义，后面直接沿用定义

| 做法 | 示例 |
|------|------|
| 定义术语 | "已解锁斗士"、"未解锁斗士" |
| 统一用语 | "新皮肤"、"初始皮肤" |
| 后续引用 | 直接使用定义的术语 |

**作用**：避免重复描述，保持用例一致性

### 原则2：环环相扣（测试顺序）

**做法**：尽量按测试顺序检查，形成流程链

```
获得 → 使用 → 激活 → 装备 → 验证 → 重进确认
```

### 原则3：拆解再重组

**做法**：简单的单规则验证完，再做组合

| 阶段 | 验证内容 | 示例 |
|------|----------|------|
| 简单 | 单规则 | 单个使用-限时、单个使用-永久 |
| 组合 | 多规则 | 先限时再永久、同道具连续使用 |

### 原则4：清晰引导提示

**做法**：无法完全拆解时，给出清晰的引导

| 引导方式 | 示例 |
|----------|------|
| 参考引用 | "与上方xx模块的预期一致" |
| 对照模块 | "对照【显示场景】模块" |
| 组合抽查 | "2种使用方式+3种道具任意组合抽查3种即可" |
| 合并检查 | "结合下面的buff生效模块一起检查" |

## 十三、高级设计模式（V7.4新增）

### 模式H：维度矩阵覆盖

适用于：多角色、多位置、多类型的组合场景

**二维矩阵示例**：

| 维度1\维度2 | 类型A | 类型B |
|-------------|-------|-------|
| 位置1 | 仅位置1为类型A | 仅位置1为类型B |
| 位置2 | 仅位置2为类型A | 仅位置2为类型B |
| 位置1+位置2 | 均为类型A | 均为类型B |

**实际应用**：
```
| 主将 | 副将 | 组合 |
|------|------|------|
| 新皮肤 | 默认 | 仅主将为新皮肤 |
| 默认 | 新皮肤 | 仅副将为新皮肤 |
| 新皮肤 | 新皮肤 | 主、副将均为新皮肤 |
```

### 模式I：状态转换覆盖

适用于：有生命周期的功能（限时道具、活动、皮肤等）

**状态机示例**：
```
未解锁 → 待激活 → 已激活未使用 → 使用中 → 过期/手动切换 → 恢复初始
```

**状态变化验证**：

| 场景 | 起始状态 | 结束状态 | 验证点 |
|------|----------|----------|--------|
| 生效→失效 | 使用中 | 过期 | 立即恢复+效果失效 |
| 失效→生效 | 默认状态 | 激活穿戴 | 立即生效+效果生效 |
| 手动切换 | 使用中 | 手动切回 | 正常切换+效果变化 |

### 模式J：三类资源验证

适用于：皮肤、头像、模型等视觉资源显示场景

| 资源类型 | 场景示例 | 验证重点 |
|----------|----------|----------|
| 模型 | 主界面、编队、大地图 | 模型+动画 |
| 头像列表 | 选择列表、队列 | 头像图标 |
| 小头像 | 战报、弹窗、集结 | 小图标 |

### 模式K：即时变化 vs 不变化

适用于：实时更新与历史数据的区分

| 类型 | 场景 | 预期 |
|------|------|------|
| 即时变化 | 行军中、战斗中、集结中 | 均有正确的即时变化 |
| 不变化 | 已产生的战报数据 | 保持之前状态，不随当前变化 |

### 模式L：检查目的标注

| 基础界面 | "基础的新增界面检查" |

### 模式M：拓展点标注

**做法**：用"拓展"标注可扩展的验证点

| 标注方式 | 含义 |
|----------|------|
| 拓展 | 当前版本可选，后续版本必测 |
| 可选 | 根据时间决定是否执行 |
| 抽查 | 多种组合中选择部分验证 |

### 模式N：特殊机制覆盖

适用于：有特殊交互关系的功能（附身、继承、叠加）

**背后灵/附身类场景**：

| 场景 | 覆盖点 |
|------|--------|
| A有特性，不关联B | 与其他对象效果一致 |
| A无特性，关联有特性的B | 不影响B的特性显示 |
| A有特性，关联无特性的B | A的特性正常显示 |
| A有特性，关联有特性的B | 两者特性独立显示 |
| 关联后A特性失效 | 不影响B |
| 关联后B特性失效 | 不影响A |
