# UI 多语言与屏幕适配验收

功能验收与版本日验收都先判断本次改动是否产生语言或布局适配风险，再选择检查范围；不是所有任务都要切换英语、俄语、阿拉伯语。静态影响分析只决定运行覆盖，不代表显示验收通过。用户明确要求语言/适配专项或指定语言时，沿用该范围。

## 判断显示影响与检查范围

开测前结合原需求、Jira 截图/描述、实际代码和配置变更，沿数据到界面的链路核对受影响的文案、组件、状态和显示值。配置或服务端变更可能改变长度、数值格式、字段顺序或可见区域，不能仅因没有客户端 diff 就认定不涉及适配。

| 判定 | 适用条件 | 默认检查 |
|---|---|---|
| 完整三语 | 新增界面，或修改文案/翻译键、文本布局、字体、RTL/镜像；新增动态内容可能改变换行、占位或文字与图标关系 | 对受影响界面/状态实际检查英语、俄语、阿拉伯语 |
| 定向检查 | 只改颜色、图标、按钮状态、交互入口、可见性或数值，现有文本与布局基本复用 | 先用当前语言验证本次变化及相邻区域；仅对存在依据的长文本、混排或方向风险追加对应语言，不默认三语。新增文本行或改变占位后有语言风险时升级为完整三语 |
| 不需要 | 纯服务端逻辑、计数、发奖、权限、版本迁移、协议或音效等变更，已核实不改变语言相关显示和布局 | 执行业务验收及必要界面观察，不另做多语言适配；屏幕尺寸也不自动扩展 |
| 待判定 | 变更、原图或显示链路证据不足，尚不能判断是否影响适配 | 先补查相关需求、代码/配置和实际界面；不把未知当成不需要，也不直接给全部任务加三语 |

判定依据要能定位到本次改动和显示影响，而不是只看任务标题、客户端/服务端标签或当前界面是否有文字。例如：修正邮件模板 ID 的取值，且仍使用原有模板、文案和布局，属于业务链修复，不因需要打开邮箱核对就追加三语；若同时新增邮件文案或改变附件/正文布局，则检查相应显示风险。颜色或音效调整也不自动触发翻译与屏幕适配回归。

每项记录判定、证据位置、受影响界面/状态、所选语言和选择理由；不需要时同样记录无语言影响的依据。基于充分证据按本规则作常规范围选择，无需逐项请求用户批准；用户已明确指定的语言覆盖不能自行缩减。某项已判定必要的语言暂不支持、账号不能切换或界面不可达时保留具体缺口，不能用其他语言替代通过。

## 多语言文案来源与判定口径

K1 Unity Editor（未设置 `K1D2Config.mCfgVersion`）启动时由 `I18NBootStrap.LoadGoogleSheet` 从在线翻译母表拉取当前语言并覆盖本地 `client/Assets/Res/i18n/*.tsv`；这是开发环境为便于测试设计的流程，打包前会再手动同步 tsv。

- **以 Unity 实际显示为准。** Unity 路径中文案、卡名、提示等在所选语言下显示正确即可判通过；客户端分支 tsv 暂缺对应键或内容尚未同步，不作为未通过或阻塞理由。报告注明“文案取自翻译母表，tsv 待打包同步”。
- **Unity 显示错误仍判未通过。** 母表未修正时，即使开发已手改客户端 tsv，Unity 仍显示旧文或原始键，结论保持未通过，并说明需修正翻译母表；不要以 tsv 已改替代运行截图。手改 tsv 会被后续 Jenkins 多语言导出（同一母表）覆盖，可在详情中提示。
- 真机包路径以安装包实际显示为准，该路径仍按包内资源核对；Unity 路径结论不替代真机路径。

## 两类验收共同的语言检查

以下操作适用于完整三语和定向选中的语言。只覆盖本次改动及必要相邻显示、操作区域，不遍历无关功能。

先记录原语言和实际构建、账号、设备/分辨率。通过产品现有语言设置切换，按客户端实际要求等待刷新或重启，再重新进入目标界面；核对当前生效语言与实际显示，设置回包成功、语言键存在或静态翻译表都不能代替运行截图。原语言已是目标语言时可直接检查并留证。

| 语言 | 主要显示检查 |
|---|---|
| 英语 | 常规排版、按钮/提示完整、漏译、缺失键及回退到其他语言 |
| 俄语 | 长文本截断、换行、溢出、重叠遮挡、字体缺字及按钮可读可点 |
| 阿拉伯语 | 字形与连写、RTL 阅读和布局方向、镜像关系、数字/英文混排、图标与按钮对应关系 |

每种语言都查看受影响界面的入口、正文、按钮、提示及本次改动涉及的空/错状态、奖励与数值；用户名、联盟名、时间、货币、计数等动态变量应完整且顺序正确。按实际支持的切换方式检查刷新后的显示；热切换、重登或原文/译文切换本身属于改动范围时再验证对应往返行为。

## 纳入验收计划与协作

在冻结基线前，先保存各项适用性判定，仅把完整三语或定向选中的语言检查列入原需求的用例或独立断言。沿用现有计划字段：断言 ID 可用 `TC-1/ui-en`、`TC-1/ui-ru`、`TC-1/ui-ar`，`expected/action` 写目标语言、界面、检查点和实际操作，`requiredEvidence` 包含 `ui`；保留原 `requirementIds`，不新增版本需求。

接续验收发现旧计划机械追加了无适用性的语言断言时，重新核对实际变更并保存调整理由、旧基线/计划及哈希，再按计划更新合同校准必要范围；保留已取得证据，不把未执行改写为通过，也不伪造用户排除决定。真正缺少依据或存在语言风险的断言不能借调整计划删除。

同一 Unity/账号的语言切换属于共享写操作，放在同组有序断言或不同批次；语言检查之间只是执行顺序时，不建立“上一种语言必须通过”的 `dependsOn`，避免俄语缺陷挡住阿拉伯语检查。只有实际隔离且确认语言设置不会相互覆盖的客户端/账号才可并行。

### 多项任务按语言集中验证

多项任务需要三语检查时，默认把可共用设备、账号及前置环境的任务按语言编排：先完成当前语言下各项受影响界面的检查，再切换下一种语言，减少反复刷新或重启。当前语言是英、俄、阿之一时优先从当前语言开始，否则可按英语 → 俄语 → 阿拉伯语；同一语言内沿用已确认的任务顺序。必须先满足业务依赖、易失状态和活动时间窗口；会相互消耗资源或改变前置的项目分批处理，不为集中切语破坏验证条件。

每完成一项任务的一种语言检查，立即保存该任务、界面和语言对应的结果与证据。仅部分语言完成时保持验收中，并记录已覆盖语言和剩余项；该任务全部必要语言、其他验收要求及独立收尾完成后，立即更新原文档对应项的跟进人、验收状态和结论，回读确认后按 [进度播报规则](acceptance-progress.md) 入账，不等待其他任务或整个语言批次结束。失败和阻塞也逐项保留真实状态及剩余覆盖，不因同批其他任务通过而标记完成。

原语言恢复统一安排在本次语言批次结束或交接前，逐项更新文档不触发额外的语言往返；批次中记录实际当前语言，不提前宣称原语言已恢复。

结束或交接前恢复本次切换前的原语言并回读确认；无法恢复时记录原因、当前语言和后续动作，不能写成已恢复。把切换入口、刷新/重启要求和已发现的易漏点记入分功能经验，本轮通过结论仍需本轮版本证据。

## 屏幕尺寸覆盖

仅对有尺寸或布局影响、或用户明确要求适配专项的界面选择尺寸覆盖。所选语言检查在本轮所选客户端路径分别执行，不因任务存在界面或做了语言检查就自动扩展到全部尺寸、全部功能。

已判定需要尺寸适配的功能开发验收，或用户明确要求屏幕适配专项时，按当前支持的设备、方向范围选择较窄/较小屏、常规屏、较宽或较高屏；支持平板或横屏时纳入相应端点。至少让英语覆盖主要尺寸，俄语和阿拉伯语覆盖空间最紧的关键界面，高风险动态文本或方向变化再补组合，不穷举无意义的笛卡尔积。

在所选尺寸核对安全区、刘海/圆角、首屏与滚动末端、弹窗、长文本、输入法和适用的横竖屏状态；文字、数值、图标不重叠越界，关键操作可见且可触达。记录设备型号、系统、原生分辨率、缩放/安全区及客户端构建号。模拟分辨率可辅助定位，不能代替需要真机验证的触控和安全区结论。

## 证据与通过条件

每个需要语言检查的界面/状态按下表对所选语言留记录，包含实际原尺寸截图和观察。需证明闪烁或瞬态问题时附连续帧；涉及删除、转让或付费的界面可停在确认弹窗检查显示，不为适配检查执行不可逆确认。

| 需求 / 界面 / 状态 | 语言 | 构建 / 设备 / 分辨率 | 前置与步骤 | 显示观察 / 结论 | 截图证据 | 缺口 / 下一步 |
|---|---|---|---|---|---|---|

完整三语项须英、俄、阿均取得所需实际显示证据；定向检查项须所选语言和状态取得证据。均无未解决问题，才可认为对应语言范围通过；其他验收要求仍需完成。不需要多语言的任务不以缺少三语截图为阻塞。缺某种必要语言或状态时继续补验，真实无法继续则按运行验收规则记录阻塞，不能将整项记为通过。单一语言或单一尺寸通过只证明对应覆盖；同一缺陷影响多个组合时保留各自证据，按唯一缺陷计数。

关联版本进包表时，三语检查仍属于同一需求。尚可补验的缺口保持 `running`，最终未通过或真实阻塞按 [进度播报规则](acceptance-progress.md) 入账；存在必要语言覆盖缺口时不能设置 `scopeComplete=true` 或播报该需求通过。本轮可继续项处理完后，若同时有已确认显示缺陷和语言覆盖阻塞，需求结论记 `failed`，保留各语言的失败/阻塞状态、证据与待补范围；只有覆盖阻塞而无已确认失败时记 `blocked`。恢复语言的结果一并写入收尾与留存变化。
