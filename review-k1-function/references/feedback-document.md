# 反馈文档准备与逐项维护

两类运行验收都先确定反馈落档位置并检查字段，再编排本轮计划。功能开发完成时以文档和已有反馈详细验收；版本日只把用户指定的问题加入定向复验，准备反馈表不扩大玩家体验范围。静态预检与单独建环境不因此新增在线反馈表。

## 1. 先查来源，缺链接时作出明确选择

1. 从用户提供链接、当前任务关联、私有功能经验和已有交接中查找，核对功能、版本范围、文档/工作表身份与实际权限。有唯一匹配且已授权维护的表直接复用；多个候选无法判断时只确认目标。
2. 没给链接且上述来源确实找不到时，向用户提出一个选择：**补充已有反馈表链接，还是新建反馈表（推荐）**。等待选择期间继续独立验收，新增问题、截图及待同步内容保存在本轮目录，不编造历史反馈。已有明确建表决定和位置时直接执行，不重新确认；未回答不能当作同意新建。
3. 选新建后使用已明确的文档目录、空间及共享范围；只有缺少必要位置时再问一个问题。创建后回读真实链接和工作表，按下节初始化字段，记录到本轮交接和私有功能经验。创建结果不明先查回执与目标目录，避免重复建表；协作者共用已确定的表，由协调者负责建表/补字段。
4. 已有链接但打不开、只读或无法插图，不等于不存在反馈表。先补齐具体权限/能力缺口，不能自行另建表替代指定来源。工具没有建表/补字段能力时给出待建结构，等待可用编辑路径或用户完成；本地草稿不冒充在线表。

准备记录至少包括：来源/工作表 ID、反馈表版本、可读写状态、字段映射、原始数据验证快照、缺字段及实际补建结果、待确认问题和下一步。状态区分待来源决定、待创建、待补字段/权限与已就绪；这是 Agent 维护的记录，不是新增 CLI 字段。来源和字段变化后重新核验，历史写权限不自动沿用。

## 2. 必需字段：有则映射，缺则补建

按语义识别字段，同义列直接映射，已有拆分列共同承载同一信息时保留原结构。**没有可承载所需信息的字段，就在已授权维护的原表补建缺失字段，无需逐列重复确认；不能因此重建整张表或覆盖旧数据。** 表结构被明确限制或无修改权限时，先解决受影响字段的权限，其他验收继续。

| 必需逻辑字段 / 新表建议列名 | 内容与类型 |
|---|---|
| 反馈 ID | 唯一稳定身份；可使用平台原生稳定记录 ID，否则新增文本列并分配唯一编号。排序后的行号不是身份。 |
| 关联需求/用例 | 需求稳定 ID、必要的用例/断言 ID；用于关联原需求与版本台账。无法判定时如实记待关联，不以反馈行数计需求数。 |
| 问题描述 | 标题、触发前置、复现步骤、预期与实际表现；已有分列可共同满足。保留历史原文，新问题仅依据真实观察。 |
| 问题截图 | 支持同一反馈多图/附件；保留原图并追加本次实测图。纯协议/后台问题注明无适用画面，并保留返回及日志证据。 |
| 验收 | 唯一验收状态，独立于开发处理状态。新建字段使用单选：待验收、验收中、未通过、已通过。 |
| 验收详情 | 本轮观察、结论边界、阻塞/遗漏原因、补验动作、图片对应关系和必要证据定位；正常通过且无补充时可留空。 |
| 验收环境/版本 | 本轮实际设备/账号定位、服务器实例与客户端/服务端/配置版本，可引用可访问的批次环境记录；不写凭证或猜测值。 |
| 最近验收时间 | 最近实际验证时间，含时区；未测留空，建表/整理时间不冒充实测时间。 |

已有开发状态、负责人、优先级等字段保留，不占用它们存验收结论。缺字段要补建；已有字段中信息未知则记录缺口，不补造历史数据。新表无问题时保留空表，不为填满结构虚构反馈行；正常验收结果仍在需求报告/台账中维护。

补字段或新建表按以下顺序：

1. 保存原表文字、稳定行身份、图片清单及已有下拉的选项、颜色、顺序、适用范围和其他约束。
2. 生成逻辑字段到实际列/原生 ID 的映射，只新增缺失项，不新增“本轮验收/复验结果”等重复状态列。
3. 初始化新字段类型和验证范围。新建验收字段使用上述四种状态，待验项默认待验收；既有验收下拉和历史值保持不变，建立语义映射。含义不清才确认，不擅自更换选项或颜色。blocked 等细分原因写入详情，不能映射成通过。
4. 回读字段及验证对象，确认旧数据、原图、开发状态和非目标格式保留；首次实际附图时验证追加与打开，不插入测试图片冒充问题证据。
5. 用准备后的结构建立新的反馈快照。结构变更前生成的补丁需重新定位和生成，不继续套用到新列上。

`feedback snapshot/plan/apply/reconcile` 当前只处理已有行的验收、详情与图片补丁，**不会自动创建表、补列、初始化下拉或新增反馈行**。建表补列、新问题建行及关联需求、环境/版本、时间等字段的维护，由 Agent 使用当前可用文档工具完成并回读，然后生成新的反馈快照；未知写入结果先核对，不重复建行。脚本的 `fieldMap` 至少明确 `problem / images / acceptance / details`，稳定身份由实际表和本轮记录绑定。脚本只接受既定验收值映射；原表选项语义等价但文字不兼容时，使用保留原结构的编辑路径并回读，不能声称脚本支持自定义值。

## 3. 逐项验收主线中的维护

**执行验收 → 更新对应反馈/新增真实问题 → 回读文字并逐图核验 → 保存需求结论与播报 → 按条件归档清理。** 每项及时维护，不等整轮结束；没有新问题或待复验反馈的正常通过项不制造问题行。

- 复验前按 [原图基线](runtime-acceptance.md#11-反馈原图是复验基线的一部分) 查看原图；写入按 [字段与格式保留](runtime-acceptance.md#42-反馈表字段整理与格式保留) 追加截图、维护唯一验收状态及必要详情。
- 业务观察与文档同步状态分开记录。待来源、待补字段、待同步或附件未验证时，保留已测结果与本地证据，不能宣称反馈维护完成，也不能以本地报告替代本轮要求的在线写回。可继续的文档动作继续执行，确实无法继续时明确交付缺口。
- 版本进度按 [需求级播报](acceptance-progress.md) 处理：相关维护尚可继续时保持 running；真实受阻且无其他可执行项时记 blocked；已发现确定业务缺陷则保留 failed 并披露同步缺口。未完成相关维护不能设置 scopeComplete=true 或播报通过；已保存的通过断言无需伪改为业务失败。
- 未建表或结果/附件未同步时，相关截图和导出不进入已归档清理；完成 [归档核验](runtime-artifact-cleanup.md) 后再逐文件处理。同步完成只更新实际变化的结论/状态，不用附件补传制造重复播报。

将确认后的链接、工作表、字段映射、版本及未完成维护事项写回私有功能经验，下一轮先查再问；共享 Skill 仅保留这套结构与方法。
