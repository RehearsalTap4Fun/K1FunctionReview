# 版本进包项在线状态与进度播报

用于关联版本日进包内容表的验收。在线表状态用于与其他协作者同步，必须随实际验收进度更新；本地台账不能代替它。自定义机器人播报只在用户另有明确授权时执行，不影响在线表状态维护，不创建定时任务。单功能验收未关联进包表时不生成版本总数。

## 统计与触发

以**本轮完整入队清单的一条需求**为计数单位，用稳定行 ID 或 Jira ID 去重；行号、标题、子用例数量都不能代替需求身份。同一需求的多个端、反馈项和子用例只算一项。独立版本日 AI 验收先完整读取源页签，再按下述条件生成入队清单；其他协作者负责、未入队的 `验收中` 行不计入本轮总数，本轮自己已接手的行计为 `running`。

| 状态 | 含义 | 计入 | 是否播报 |
|---|---|---|---|
| `pending` | 尚未开始 | 待验收 | 否 |
| `running` | 已开始，仍在执行或补验 | 正在验收 | 否 |
| `passed` | 当前模式下本需求的验收范围通过 | 已完成 | 是 |
| `failed` | 本需求形成未通过结论 | 未完成 | 是 |
| `blocked` | 本轮因明确阻塞暂时无法继续 | 未完成 | 是 |

总需求 = 已完成 + 待验收 + 正在验收 + 未完成。四类互斥，待验收与正在验收分别显示，不输出百分比。`blocked` 恢复补验时转 `running`；仍有可执行补验的部分验证保持 `running`。

在线原表与本地同步：尚未开始为 `待验收` / `pending`，实际开始或继续补验为 `验收中` / `running`；确认通过、未通过后分别写 `已完成`、`未通过`。只标记实际开始处理的条目，未启动的排队项保留待验收，不批量占用整版内容。

触发播报的需求终态包括通过、未通过、阻塞，消息显式显示结果；统计中的“已完成”仅计通过，未通过和阻塞计入“未完成”，不能把“测试结束”计为通过。子用例通过不触发需求完成，原运行验收的用例 `counts` 不能作为版本需求数。

两种验收模式均先按 [语言影响判断](ui-language-and-screen-adaptation.md#判断显示影响与检查范围) 记录完整三语、定向检查、不需要或待判定；仅将必要语言断言计入原需求覆盖，不新增版本需求。不需要多语言的任务不因没有三语截图而阻塞；缺少已判定必要的语言证据不能设置 `scopeComplete=true` 或播报通过。尚可补验保持 `running`，形成未通过结论或真实无法继续时分别记 `failed` / `blocked`。

本轮应维护的反馈文档按 [反馈准备与维护](feedback-document.md) 检查来源、必需字段、写回和附件。缺字段先补建；待建表/同步且仍可继续时保持 `running`，真实无法继续时为 `blocked`；已有确定业务缺陷则保留 `failed` 并披露文档缺口。未完成相关维护不能设置 `scopeComplete=true` 或播报通过；没有问题的正常验收不要求虚构反馈行。`record` 不自动执行这些在线检查，由协调者核验并将依据存入结论证据。

每次需求结论持久化后立即发送。相同 `eventId` 重放幂等；复验后相同状态与相同结论不重复播报，新结果或改变的结论再播报。仅证据文件变化不制造新结论。新版本日、不同源表或不同验收模式使用各自台账，不能把功能开发完成时的结论当版本日结果，也不能在 Unity 或真机任一路径未完成时把需求记为通过。

## 版本清单与统一台账

### 版本日验收的选单与在线状态

- 进包表为 [K1 版本日必进项](https://alidocs.dingtalk.com/i/nodes/mExel2BLV549Xda9IDEajDabWgk9rpMq)。任务明确指定页签时用该页签；写“最新数字页签”时先列出全部页签，选数值最大的页签，并在本轮台账固定其工作表 ID、名称和读取时间。分页读取完整数据，不依赖界面当前筛选或可见行。表头按名称定位“状态”“合并状态”“JIRA单”；无法唯一定位时先核对，不猜列号。
- 常规首次自动入队仅限源表 `状态=待验收` 且 `合并状态=已合进dev` 的行。`验收中` 行先核执行归属：只有本轮自己已写入并回读、当前归属仍一致的行可以续跑；其他协作者或归属不明的行排除且不抢占、不修改。其余状态除获准的定向复验外不入队。按稳定行身份与 Jira ID 去重，缺 Jira ID 或一行对应多单时先核对映射，不将整表当成待测清单。选 `qa` 时仍须逐项核实目标改动已进入 qa；dev 合入状态不能替代 qa 证据。
- Pango 任务填写“上次 AI 测试任务号”时，除上列常规行外，可追加上次任务明确判为 `failed`、同一原 Jira 且源表当前仍为 `未通过` 和 `已合进dev` 的行作为定向复验；用户明确指定的复验沿用其授权范围。接手后同样先写在线 `验收中` 并回读。不能接管他人负责或归属不明的 `验收中` 行；上轮通过且源表已完成的行不因此重新入队。
- 每项按原 Jira 实际类型决定范围：缺陷/故障与快速任务尚未完成首次验收，走测试用例验收；其他项按版本日玩家体验范围验收。先保存本轮可复核的报告和证据，再决定结论。
- 实际开始处理该项（包括专用环境前置或补验）之前，刷新并确认入队资格，将该行状态设为 `验收中`，在既有跟进人或验收详情中记录执行者、批次标识及带时区的开始时间；保存工作表 ID、稳定需求身份、写前状态和写后回读证据。保留状态下拉、颜色和其他人已有内容，不新增第二个验收状态列。写入或回读失败时先恢复在线同步，再启动该项操作。
- 形成通过或未通过结论后，写前重新核对稳定身份、合并状态及仍归本轮自己的 `验收中`，分别更新为 `已完成` 或 `未通过` 并回读；定向复验同样经过此过程。若归属、状态或身份被其他协作者改变，停止写入并记录冲突，不能覆盖他人结果。必要反馈及在线状态回写分别核验。
- 仍在执行、部分验证或继续补验时，在线保持 `验收中`，不能因尚无最终结论退回待验收。确因阻塞或中断而停止处理时，仅将自己负责的行释放为 `待验收`，在详情写清已测内容、停止原因及续验动作；已有明确失败且本轮结束则写 `未通过`。失联后不能仅凭超时接管他人的行。共享台账 `blocked` 或统计“未完成”不等于源表 `未通过`；回写失败保留待同步记录，不伪称成功。

### 每项开测前刷新源表状态

在每项首次开始验收、切换到该项或恢复其补验前，重新读取一次指定工作表中该需求的当前原行；按稳定行身份和 Jira ID 定位，复核“状态”“合并状态”及本轮用户排除范围。整轮开测快照、旧台账、历史验收详情和先前的 `next` 输出只用于定位，不能代替这次刷新。

- 首次开始或重新接手已释放的条目，须刷新后仍符合常规选单或获准复验条件，先写在线 `验收中` 并回读，再记录本地 `running` 和执行游戏操作、GM 前置或后续子用例。继续处理本轮自己的 `验收中` 行时，复核当前归属一致即可，不因其不再是待验收而跳过自己。
- 若已变为 `已完成`，停止该项并保留已有证据；若 `验收中` 归他人或无法确认归属，停止且不抢占。其他不再符合条件的状态同样处理；用户明确指定复验时沿用其范围，但不覆盖他人占用或结果。旧队列和旧本地 `running` 本身不能证明当前在线归属。
- 保存读取时间（含时区）、可取得的源表修订号、稳定身份、当前状态、执行归属及继续/跳过决定。支持条件更新时使用源修订号；不支持时执行写前刷新、最小写入与写后回读，不把此过程声称为原子锁。发生冲突先核对，不盲目重放。
- 刷新失败或无法确认当前状态时，先暂停该项的运行操作并恢复读取；其他独立项仍可继续。形成结论后的写前重读与写后回读仍按上文执行。

1. 使用有权限的文档工具完整读取进包表，按版本日过滤，读完分页与筛选外的需求，记录来源版本/内容哈希及带时区的读取时间。明确源表状态映射，不能把“开发完成”当“验收通过”。无法确认已有验收结果的需求从 `pending` 开始。
2. 同一源表 + 版本日 + 验收模式共用一个持久目录，例如 `<workspaceRoot>/.local/acceptance-progress/<table-id>/<YYYY-MM-DD>/<mode>/`。启动时先检查该目录，有 `progress.json` 就 `status` 续跑；已获机器人授权时另处理 `flush`，禁止为各协作者或每个会话另建台账。
3. 仅首次运行使用 `init`。`source.complete=true` 是协调者对完整读取的声明，脚本不能验证远端是否仍有未读行。未读全时不能填写该值或发布猜测的总数。初始化保留可靠的已有状态，但不补发历史完成项。
4. 每条需求通过上述刷新、在线 `验收中` 写入和回读后，才 `record` 为 `running` 并开始运行操作。协调者保存在线归属与状态回执；旧执行脚本若只允许 `待验收` 或一律跳过 `验收中`，须按上述规则适配本轮自己的行，不能因此省略在线同步。协作者交付需求 ID、结论与证据，由总协调者入账；本地锁/revision 不能代替在线归属核对或 Unity/账号隔离。
5. 需求验收结束后，保存/回读报告或反馈结果，将在线状态更新为最终结论并回读，再 `record` 本地结论；有机器人授权时才发送。`passed` 必须确认用户所选路径及全部必要范围和收尾已完成、文档基线有效。证据包含需求 ID、版本日、模式、范围、观察及在线状态回执；文件哈希校验不替代真实性判断。
6. 源表状态、表格增删或标题变化导致当前清单变化时重新完整读取，用 `sync` 更新清单并提供 `expectedRevision`；成员变化另填 `reason`。现有状态必须与台账相同，外部协作者的新结论先按 `record` 入账，不能被快照覆盖。新需求从 `pending` 开始。移出版本的需求不再计入当前总数，原清单与已产生播报保留历史。暂时阻塞的需求不能从清单删除。

`init` 请求见 [清单示例](../assets/acceptance-progress-snapshot.json)。`record` 请求见 [结论示例](../assets/acceptance-progress-record.json)。示例数据不是实际验收证据。

以下命令在 Skill 目录执行。台账写入用户工作区，禁止写入三端正式 K1 仓库。`record` / `flush` CLI 会尝试发送队列，仅在机器人已获授权时调用；未获授权时，使用 `acceptance.progress.ProgressStore.record(request)` 仅保存本地状态，不调用 `flush`，在线表状态仍照常更新。

```powershell
python scripts/acceptance_progress.py init --store-dir <持久台账目录> --request <完整清单.json>
python scripts/acceptance_progress.py status --store-dir <持久台账目录>
python scripts/acceptance_progress.py record --store-dir <持久台账目录> --request <需求状态或结论.json>
python scripts/acceptance_progress.py flush --store-dir <持久台账目录>
```

也可使用 `python scripts/acceptance_workflow.py progress <action> --run-dir <持久台账目录> --request <请求.json>`；请求可选 `robotConfig` 只传私有配置路径。独立 CLI 用 `--config`。完整命令参数见 `--help`。

`record` 必填 `eventId`、`itemId`、`expectedItemRevision`、`status`。开始/补验的本地接口只需这四项，但它不自动更新在线表，协调者必须先完成在线 `验收中` 写入与回读。结论另填 `conclusionFinal=true`、简洁稳定的 `conclusion` 和已保存的非空 `evidence` 文件绝对路径；通过还需 `scopeComplete=true`。ID 一旦用于某次提交，重试必须原样复用；新结论使用新 ID。revision 冲突先 `status` 核对同一需求的最新记录，不盲目改版本号重放旧结论。

## 发送与恢复

需求更新、进度快照和待发送事件写在同一个原子文件中。消息包含需求标题、结果、验收模式、版本日、四类数量，以及北京时间记录时间和唯一播报编号。并发结果按保存顺序各生成一次进度快照；消息数字对应**该结论保存时刻**，重试保留原时间与快照，不能冒充当前最新状态。

`record` 默认自动尝试发送；`flush` 在任务恢复、等待下一步和收尾时调用，处理已到期重试。没有后台常驻进程；任务停止时队列留存，下次恢复继续。一次最多处理 5 条，单次 HTTP 超时 5 秒；每台账一分钟至多尝试 15 次。高频积压留存，验收继续。

- 只有钉钉返回明确成功才标记 `sent`；HTTP 成功但响应不完整不算送达。
- 明确未送达（如 DNS/拒绝连接、明确 API 拒绝）保留 `pending`，30 秒、120 秒后可重试；每轮最多 3 次，之后 `failed`，报告错误码并待处理。HTTP 429 按 `Retry-After` 暂停当前台账发送，缺少有效值时至少等待 60 秒，不循环强发。
- 超时、连接中断、无效回包、服务端异常及发送中进程退出标为 `unknown`。不自动重发；按播报编号、版本日、标题和时间查群消息。现有自定义机器人发送接口没有自动查询送达能力，不能从“没拿到回执”推断没发出。
- 保留群回读/用户核实证据后，用 `resolve` 请求：`sequence` 为播报序号，`outcome` 为 `sent` 或 `not_sent`，`evidence` 为非空证据文件绝对路径列表。`sent` 结束；明确 `not_sent` 才重新入队，随后 `flush`。不确定就继续保留 `unknown`，其他需求照常验收与播报。
- 凭证缺失、通知失败不会回滚验收结论。命令输出中的 `notification.error` / `notifications` 必须交接，不能只看退出码认定所有消息已发送。收尾报告列出积压、失败和待核对播报。

`preview` 只展示已入队消息，不发送；`status` 不展示 Webhook。外部异常只保存脱敏错误码。

文档结果及附件核验后按 [过程文件清理规则](runtime-artifact-cleanup.md) 删除无依赖的上传源和中间副本；保留 `progress.json`、需求结论证据与送达核对材料，不能删除待发送/未知事件恢复所需文件。清理不新增需求结论或重复播报，不因无关清理延迟已形成结论的发送。

## 机器人私有配置

群聊和 Webhook 由用户指定。默认读取 `~/.codex/private/review-k1-function/progress-robot.local.json`；环境变量 `K1_PROGRESS_ROBOT_CONFIG` 或 `--config` 可覆盖。配置格式见 [私有配置模板](../assets/progress-robot.example.json)。密钥仅留本机，不能复制到 Skill、Git、请求样例、日志或报告。接收者分享 Skill 后配置自己的机器人。

消息标题和正文固定包含 **进度播报**，匹配本轮用户设置的自定义关键词；不 @ 全员。脚本为事件触发发送使用 Webhook，只有已授权的进包验收需求结论会发送。配置校验只读：

```powershell
python scripts/acceptance_progress.py check-config
```

校验通过只说明本地配置可读、格式有效，不证明群归属、Webhook 有效或已真实送达。空示例不能发送。用户授权范围之外的演示/联调消息另行明确授权；本地测试使用模拟传输，不向真实群发送虚构验收进度。

接口参考：[钉钉自定义机器人](https://open.dingtalk.com/document/robots/custom-robot-access)、[机器人安全设置](https://open.dingtalk.com/document/robots/customize-robot-security-settings)。
